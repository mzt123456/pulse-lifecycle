范围：设备全生命周期管理系统（网络版）新增的 AI 模块
分支：`feat-ai-assistant`
环境：后端 http://127.0.0.1:8000，开发库为容器中的 MySQL 8.0（宿主机 3307）

## 二、关键设计与取舍

**两条抗幻觉约束（都写进了用例）**

1. 检索为空时不调用模型，直接回答「未找到相似案例」——语料里没有的东西，让模型自由发挥只会得到编造的原因；
2. 模型给出的引用必须能在本次检索结果里对上，对不上的引用一律丢弃；一条都不剩时置信度强制降为「低」。

**降级是常态路径，不是异常处理。** 没有配置 Key、超时、返回不是 JSON，接口都退化成「只返回相似案例列表」，
并带上 `degraded` 与原因。检索链路本身不依赖模型，所以模型故障不影响页面可用。

**不引入向量库。** 语料当前 41 条（真实 1 条 + 仿真 40 条），内存倒排索引单次检索在毫秒级，
部署向量库是过度设计。语料上到十万级或需要跨语言语义泛化时再换，检索层入参与出参不变。

**BM25 自己实现。** 四十余行代码，换来的是能做结构化预过滤、返回命中词解释、按文档频率过滤无区分度词——
这几项用现成库都要另外写胶水。

## 三、实测数据

### 检索质量（40 条口语描述 → 规范案例，标准答案是案例自身）

同一脚本内对比，两列口径完全一致：

| 指标 | 基线（无词典、无扩展） | 当前（行业词典 + 同义词扩展） |
| --- | --- | --- |
| Recall@1 | 47.5% | 92.5% |
| Recall@3 | 50.0% | 97.5% |
| Recall@5 | 52.5% | 97.5% |
| 故障类型命中@3 | 55.0% | 97.5% |

复核时间 2026-10-12，命令 `python eval/retrieval_eval.py` 与 `python eval/retrieval_eval.py --plain`，
两条数字当场可复现；早先版本记的基线（52.5% / 65.0% / 72.5%）与当前脚本对不上，已按实测更正。

提升来自两处，都是实测发现的问题：

1. **领域词被切碎。** jieba 通用词典里没有「阀芯」「油位」，会把它们切成单字，而检索层丢弃单字——
   "阀芯有点卡"的实际查询词变成「有点 脉冲 连不上」，关键信号直接消失。加入行业术语后，索引与查询共用同一套切分。
2. **同一件事两种说法。** 现场说「声音不对，咔咔响」，案例库写的是「动作时有明显异响」；「压力保不住」对上「密封面渗漏」。
   检索前把口语说法扩展为规范表述（只作用于查询侧）。

**必须说清的一点：评测集与同义词表同源。** 口语查询取自仿真案例自带的「口语表述」，同义词表也是照这些对照整理的，
所以这两个数字偏乐观，属于上界。真实故障数据迁移到位后要重新评测，届时指标口径不变。

### 端到端（真实 DeepSeek 调用）

| 场景 | 结果 |
| --- | --- |
| 电气故障（带故障类型过滤） | 2.2 秒，`degraded=false`，置信度「中」，3 条原因均带引用，含 1 条真实故障记录 |
| 口语描述「咔咔响、阀芯卡」 | 1.8 秒，召回 2 条机械类案例，结论与引用对应 |
| 口语描述「压力保不住」 | 1.9 秒，召回 5 条密封类案例，模型补充了「需说明渗漏部位与保压曲线」 |
| 与设备无关的描述 | 20 毫秒返回「未找到相似案例」，未调用模型 |

模型不可用时（例如运行环境无出网权限）接口返回 `degraded=true` 与降级原因，仍能给出相似案例列表，
这一点在沙箱内实测过：`WinError 10013` 被捕获并降级，接口没有 500。

## 五、P1：Agent 工具、MCP 与技能机制

| 序号 | 内容 | 说明 |
| --- | --- | --- |
| 1 | 工具层 `app/ai/tools.py` | 六个查询工具 + 一个诊断工具，全部复用现有 service，不写 SQL |
| 2 | Agent 循环 `app/ai/agent.py` | 手写 function calling 循环，最多 5 步，超限带着已有数据收尾 |
| 3 | 接口 `POST /api/v1/ai/ask` | 登录即可提问，数据可见范围由工具粒度的权限点决定 |
| 4 | 技能 `app/ai/skills/` | 索引常驻 + 正文命中才展开 + 参考资料显式引用才读 |
| 5 | MCP Server `app/mcp/server.py` | 同一套工具定义的第二个出口，stdio 与 streamable-http 两种传输 |
| 6 | 只读资源 | `pulse://corpus/stats`、`pulse://audit/recent` |

**权限不绕过，做在两处。** 没有对应权限点的工具**不暴露给模型**（模型连尝试的入口都没有），
`run_tool` 再校验一次；实测中模型主动调用了一个没暴露给它的工具，被挡下并把错误如实写进了回答。

**审计按调用记。** 每次工具调用写一条 `object_type=ai_tool` 的审计，含参数摘要、成功与否、耗时，
挂在当前事务上。`pulse://audit/recent` 资源可以直接把最近的调用记录读出来核对。

**技能按需加载的意义可以量化。** 常驻提示词里只有技能索引；全部技能正文与参考资料一次塞进去是
索引的三倍以上字符量。接口返回体带 `context_chars`，一眼能看出省了多少。

**MCP 是出口不是第二套实现。** 工具定义、权限校验、审计都在 `tools.py`，
MCP 侧只做协议适配与身份解析（stdio 用服务账号 `MCP_USERNAME`，工具层仍按该账号权限过滤）；
只暴露查询工具，写操作不开放。

### 实测中出现并修掉的三个问题

1. **诊断工具没进注册表。** Agent 报"没有名为 diagnose_fault 的工具"，模型如实转述而不是编答案——
   这反而证明了抗幻觉约束在起作用。修法是给 `run_tool` 加 registry 参数并由本轮可用工具构成。
2. **设备型号被当成仪器类型硬过滤。** 开发库里型号是"演示脉冲器"这类自由文本，
   拿它过滤后语料一条都搜不到。改为"型号确实属于仪器类型字典取值时才当过滤条件"。
3. **日志污染 stdio 通道。** 日志默认写标准输出，而 stdio 传输下标准输出是 JSON-RPC 通道，
   一行日志就让客户端解析失败。给日志配置加了输出流参数，MCP 侧固定走标准错误。

### 端到端实测（真实 DeepSeek + 真实工具调用）

| 问题 | 工具链 | 耗时 | 结果 |
| --- | --- | --- | --- |
| 设备整体情况怎么样 | `query_overview` | 4.8 秒 | 4 台设备、3 个未解决故障、1 项低库存，并指出故障比待维保更该先处理 |
| 耗材还剩多少、有没有低库存 | `query_consumables` ×2 | 5.3 秒 | 2 种耗材、1 种低于安全库存，并提醒其中一条像是演示数据 |
| PLT-DEMO-1 掉压是什么原因 | `query_equipment` + `query_fault_history` + `diagnose_fault` | 6.6 秒 | 给出设备台账与历史记录，指出历史案例与本现象不一致，不硬套结论 |

`query_equipment`、`diagnose_fault`（真实模型返回 `degraded=false`）→ 读取两个资源全部成功。

## 六、评测补齐：原因匹配率、无结果准确率、P95 与单次成本

脚本：`backend/eval/diagnosis_eval.py`。评测集来自仿真案例自带的「口语表述」，标准答案就是该案例的规范原因——
这条设计让原因匹配率可以自动判定，不需要人工标注。

### 指标（真实 DeepSeek 调用，40 条案例 + 10 条域外问题）

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 检索到案例比例 | 100.0% | 40 条口语描述全部召回到案例 |
| 原因匹配率（首位） | 92.5% | 模型第一条原因与标准原因一致 |
| 原因匹配率（前三位覆盖） | 97.5% | 前三条原因里包含标准原因 |
| 无结果准确率 | 90.0% | 10 条域外问题，9 条正确回答"未找到"且不调用模型 |
| P50 延迟 | 1809 ms | 端到端，含检索与模型 |
| P95 延迟 | 2443 ms | 同上 |
| token 均值 | 输入 341 / 输出 123 | 单次诊断；按 1 元/百万输入、2 元/百万输出估算约 0.0006 元/次（以官网当期价格为准） |

### 为了拿到"无结果准确率"做的一次规则校准（值得记）

第一版跑出来只有 80%，两条域外问题被误召回：

- 「食堂午餐菜单这周有调整吗」→ 靠**"调整"**命中「调整脉冲参数」
- 「如何申请软件著作权登记」→ 靠**"软件"**命中「地面软件提示通讯超时」

**先试了分数阈值，不行。** 实测后把数据摊开看：误召回得分 2.57 与 3.39，真实命中里最低的是 2.64、3.07——
分布重叠，任何阈值都会同时砍掉真命中和误召回。

**再试了查询词覆盖率下限（至少命中一半查询词），也不行。** 无结果准确率上到 100%，
但 Recall@1 从 92.5% 掉到 80%：口语描述本身词多，同义扩展又把关键概念折叠成一个词
（"声音不对/咔咔/响声"都映射到"异响"，命中词数只有 1），覆盖率判据把真命中一起判死。

**最后定的是"单个命中词的稀有度"规则**：命中两个以上词直接算相关；只命中一个词时，
该词出现的文档数不能超过语料的 5%（41 条语料即最多 2 篇）。这样"调整"（3 篇）被挡下，
而"异响""重启"（各 1 篇）正常通过，两个指标同时保住：Recall@1 92.5%、无结果准确率 90%。

**剩下那 10% 是故意留着的。**「软件著作权」与「地面软件」是同一个词的不同含义，
纯字面检索无法区分——这正是引入向量检索的正当理由，写进遗留事项而不是靠调参掩盖。

## 七、前端对话界面

后台新增「智能助手」页（`/assistant`），两个模式共用一个输入区：

| 文件 | 内容 |
| --- | --- |

### 实测（浏览器里真跑）

| 场景 | 结果 |
| --- | --- |
| 故障诊断：示例"下去之后声音不对，咔咔响，阀芯有点卡" | 置信度中、1735 ms、token 490，两条原因带 C1/C2 引用 |

### 过程中修掉的两个问题

1. **模型的 Markdown 被当纯文本显示**。数据问答的回答里有表格和加粗，前端用 `white-space: pre-wrap`
   直接输出，页面上出现一堆 `|` 和 `**`。改成用 markdown-it 渲染，并关掉原始 HTML
   （模型输出属于不可信内容，不能直接注入页面）。
2. **默认 15 秒超时对 AI 接口太短**。多步工具调用实测要 4～11 秒，加上网络与模型抖动会顶到上限，
   这几个请求单独放宽到 90 秒。

前端 `typecheck`、`vitest`（6 项）与 `build` 全部通过，智能助手页按路由懒加载（约 10 KB）。

## 八、多轮对话

数据问答支持追问，设计上按"受控多轮"来做，不是把聊天记录整体塞给模型：

| 约束 | 做法 | 原因 |
| --- | --- | --- |
| 只带问答正文 | 历史里只有 user / assistant 文本，工具调用与结果不回灌 | 省上下文；工具结果是最占空间、也最容易被误当成当前事实的部分 |
| 最多 6 轮 | 服务端截断，接口层限制最多传 8 条 | 防止上下文无限增长 |
| 明示历史可能过时 | 带历史时提示词追加一段：涉及具体数据必须重新调用工具 | 库存在变、工单在变，模型照抄历史数字就是错的 |
| 技能继承 | 技能选择把最近两轮用户提问一起纳入 | 追问句（"那还有别的可能吗"）本身没有触发词 |
| 诊断保持单轮 | 诊断接口不带历史 | 现象重新描述一遍比带上下文更准 |

顺带修掉一个技能选择的缺陷：原来的评分只看命中触发词个数，一字触发词（"井"）和
"原因"会打平，平票后按目录顺序决定，结果把追问分给了错误的技能。现在评分改成
**命中触发词总长度 → 命中个数 → 技能显式优先级**，并把数据技能里的一字触发词"井"
换成"井号 / 下井 / 井深"。写入实现时还踩了个小坑：优先级一度让"零命中"的技能也能胜出，
被"无关问题不应选中技能"的既有用例当场拦住，加了"必须至少命中一个触发词"的门槛。

### 实测（浏览器里追问）

| 轮次 | 问题 | 结果 |
| --- | --- | --- |
| 第一轮 | PLT-DEMO-1 最近一次维保是什么时候，结果怎么样 | 3172 ms，答出工单 WX20261001001、三级维保、结果合格 |

## 九、相关性重排：把无结果准确率从 90% 补到 100%

### 为什么不是向量检索

先按原计划探了路，两个结论：

1. **DeepSeek 没有 embedding 接口**。`GET /models` 只返回 `deepseek-flash`、`deepseek-v4-pro`；
   `POST /embeddings` 返回 404。
2. 本地跑 BGE 这类向量模型要装 torch 并下载模型权重，对这套演示环境过重。

所以改用**对话模型重排**：同一个已经在线的模型，零新增依赖，判断标准还能写成业务规则
（提示词里明确写"不要因为撞到同一个词就判为相关"，并举了软件著作权的例子）。

### 实现与取舍

| 设计点 | 做法 | 理由 |
| --- | --- | --- |
| 打分 | 逐条 0-10 分，低于阈值（默认 5）丢弃 | 阈值可配，便于按业务调整 |
| 全部丢弃 | 按"未找到"处理，**不进入生成环节** | 这正是抗幻觉的第二道闸门 |
| 失败处理 | 调用失败或返回格式不对 → **放行**（fail-open） | 重排是精度优化，不该让诊断整体不可用 |
| 可替换 | `Reranker` 是协议，诊断流程只依赖接口 | 将来换向量检索或 bge-reranker 只加一个实现 |
| 成本口径 | 重排自身的 token 计入返回体 | 否则单次成本是虚低的 |

### 指标对比（真实模型，40 条案例 + 10 条域外问题）

| 指标 | 关闭重排 | 开启重排 |
| --- | --- | --- |
| 无结果准确率 | 90.0% | **100.0%** |
| 检索到案例比例 | 100.0% | 100.0% |
| 首位原因命中 | 92.5% | 92.5% |
| 前三位原因覆盖 | 97.5% | 97.5% |
| 重排动作 | — | 40 次执行，共丢弃候选 22 条 |
| P50 / P95 延迟 | 1693 / 1983 ms | 3098 / 4001 ms |
| 生成 token 均值 | 输入 341 / 输出 118 | 输入 312 / 输出 103 |
| 重排 token 均值 | — | 338 |

结论要连着代价一起说：**抗幻觉能力换来的是延迟翻倍与 token 增加约六成**。
所以做成了开关（`AI_RERANK`），对延迟敏感的场景可以关掉；两种配置的指标都留在上面，不挑好看的报。

## 十、向量检索：接入 qwen3.7-text-embedding 与五组配置消融

模型选型：通义百炼 `qwen3.7-text-embedding`（多语言统一向量模型，支持 256~2560 维，
实测取 1024 维）。自检结果：3 条文本 695 ms，故障 vs 故障相似度 0.36、故障 vs 无关 0.20，
区分度正常。

接入方式是**混合检索**而不是替换：向量侧与关键词侧各取候选，归一化后加权融合。
一个刻意的设计：**向量分数不做相对归一化**，保留绝对余弦——否则任何查询都会产生一个
"满分候选"，下面第 1 条结论里的问题就更没救了。

### 五组配置（真实模型，40 条案例 + 10 条域外问题）

| 配置 | 无结果准确率 | 首位原因命中 | 前三位覆盖 | P50 延迟 | 单次 token |
| --- | --- | --- | --- | --- | --- |
| 关键词 BM25 | 90.0% | 92.5% | 97.5% | 1693 ms | ≈459 |
| 纯向量 | 0.0% | 80.0% | 100% | 1898 ms | ≈681 |
| 混合 | 0.0% | **95.0%** | 100% | 2136 ms | ≈677 |
| 关键词 + 重排 | 100% | 92.5% | 97.5% | 3098 ms | ≈753 |
| **混合 + 重排（生产）** | **100%** | **95.0%** | **100%** | 3594 ms | ≈1265 |

### 三条结论

1. **纯向量会把"未找到"能力打没。** 余弦相似度永远大于 0，域外问题也能找到"最像"的案例，
   无结果准确率从 90% 掉到 0%——抗幻觉失效。这条不实测很容易漏。
2. **向量提升的是排序，不是替代。** 首位原因命中 92.5% → 95.0%，前三位覆盖 97.5% → 100%；
   但纯向量的首位命中反而只有 80%，低于关键词——说明在这套中文行业语料上，
   行业词典 + 同义扩展的关键词检索本身很强，两者是互补关系。
3. **重排是相关性闸门。** 只有"混合 + 重排"同时拿到最好排序和 100% 无结果准确率。
   生产配置因此是两者叠加。

### 实测中的两次"设计有效"证据

- **重排返回的 JSON 解析失败过一次**（`Expecting ',' delimiter`），fail-open 生效：
  按原顺序放行，那一问照常给出答案，整轮诊断没有失败。
- **口语改写命中**：`打压的时候压力慢慢的往下掉，保不住` 这条说法在纯关键词下靠同义扩展能命中，
  接入向量后首条直接是「打压试验中压力缓慢下降」，融合分 0.878、重排分 10——
  这正是向量带来的语义泛化。

## 十二、Agent 编排改用 LangGraph 状态图

原来的 Agent 是一个 `for step in range(1, max_steps+1)` 循环。现在改成显式状态图
（`app/ai/graph_agent.py`）：

```
START → prepare → plan ─┬─ 要调工具 → execute_tools ─┬─ 预算还有 → plan（回边即循环）
                        │                            └─ 预算用尽 → partial → END
                        └─ 给结论 / 模型失败 → END
```

### 设计取舍

| 决策 | 做法 | 理由 |
| --- | --- | --- |
| 状态放什么 | 只放"本次问答的过程数据"（消息、步骤、预算、结论） | 状态是过程，运行环境不该混进去 |
| 运行环境放什么 | `context_schema` 承载会话、调用者、模型、工具清单 | 这些跨节点不变，放进 state 只会让状态难读 |
| 预算怎么控 | `budget_left` 在 `execute_tools` 里扣减，归零走 `partial` 收尾 | 循环次数由状态决定，不依赖外部计数 |
| 递归上限 | `recursion_limit` 按步数换算设成有界值 | 图深度本身有界，不靠框架默认值兜底 |
| 失败怎么办 | 图异常 → 自动回退手写循环，并在 `orchestrator` 字段标明 | 编排方式不该成为可用性的单点 |

用到的能力：`StateGraph`、条件边、环、状态字段增量合并、运行上下文。
**没用**：检查点持久化、人工介入中断、子图与多智能体交接——单进程一问一答用不上，
写进 README 免得被追问时含糊；并注明将来需要"执行前人工审批"时会把中断加在 `execute_tools` 之前。

### 验证

- 行为一致性：既有的 24 项编排用例直接跑在状态图上全部通过；另加一项**对照用例**，
  同一输入分别走 `langgraph` 与 `loop`，断言答案、工具调用、步骤序列完全相同。
- 结构可读：一项用例断言编译后的图里存在 `prepare / plan / execute_tools / partial` 四个节点。
- 兜底有效：一项用例把图执行打成异常，验证自动回退到手写循环且返回体里标明。
- 真实链路：重启后问"现在设备整体情况怎么样"（`orchestrator=langgraph`、1 次工具调用、4.9 秒）、
  带一轮历史的追问"那台设备历史上出过什么故障"（正确解析为 PLT-DEMO-1、2.8 秒）。

后端全量 198 项测试通过。

## 十三、编排与工具层改用框架的主流写法

前面把两处"手写但没有业务价值"的实现换成了框架写法，业务插桩仍然留在自己手里。

### 一、工具定义：手写 JSON Schema → `@tool`

原来每个工具是一个 `ToolSpec`，`parameters` 是手写的 JSON Schema。问题有两个：参数名改了忘改 schema、
参数校验写两遍。现在定义写在 `app/ai/tool_defs.py`：

```python
@tool(parse_docstring=True)
def query_equipment(
    context: Annotated[ToolContext, InjectedToolArg],
    keyword: str | None = None,
    status: str | None = None,
    limit: int = 10,
) -> dict:
    """按编号关键字或状态查询设备台账。

    Args:
        keyword: 按脉冲编号或型号模糊匹配。
        status: 设备状态，取值：在用、待命、维保、报废。
        limit: 返回条数，默认 10，最多 50。
    """
```

- **描述**来自 docstring，**参数说明**来自 `Args:` 段（`parse_docstring=True`），**类型与默认值**来自注解；
- 运行上下文（会话、调用者、来源 IP）用 `InjectedToolArg` 注入，`convert_to_openai_tool`
  会把它从模型可见的参数里剔除——模型看不到，也伪造不了；
- 桥接函数 `to_spec()` 把 `@tool` 对象转成 `ToolSpec`，**权限点在这里显式绑定**
  （`@tool` 没有这个概念），执行仍走 `tools.run_tool`。

### 二、消息与历史：手拼字典 → `add_messages` + `trim_messages`

图的状态从 `list[dict]` 改成 `Annotated[list[AnyMessage], add_messages]`：

- 节点只返回**新增**消息（`AIMessage` / `ToolMessage`），追加交给 reducer，不用自己维护列表；
- `AIMessage(tool_calls=[...])` 自带工具调用结构，替代了手写的 `_assistant_message`；
- 历史裁剪换成 `trim_messages`（按字符预算、`strategy="last"`、`include_system=True`、`start_on="human"`），
  替掉手写的 `_normalize_history` 截断逻辑，也不会裁出以 assistant/tool 开头的非法序列；
- 与模型的边界用 `convert_to_openai_messages` 转一次，客户端仍然收发 OpenAI 协议的字典。

### 三、哪些**没有**交给框架（这是有意的）

| 保留在自己手里 | 原因 |
| --- | --- |
| `tools.run_tool` 执行工具（不用 `ToolNode`） | 执行前要按权限点过滤、执行后要写审计，这两个插桩点框架没有 |
| 工具的权限绑定 | `@tool` 只有名字/描述/schema，没有业务权限点的概念 |
| 预算、禁止重复调用、降级与"未找到"判定 | 属于业务语义，写在节点里 |
| 手写循环（`AI_ORCHESTRATOR=loop`） | 保留作对照与兜底：图异常时自动回退 |

### 验证

- 后端全量 198 项测试通过（含 28 项编排用例、11 项 MCP 用例）；
- 真实链路：`/ai/ask` 走图编排，`编排=langgraph`、两次工具调用、3.6 秒返回；
  工具参数由 Pydantic 校验，未知参数会被过滤后再执行；
- `/ai/diagnosis` 未受影响（`通道=hybrid`、重排生效），确认这次改动只动了编排与工具定义层。

## 十四、模型调用改用 ChatOpenAI

前面两处改成了框架写法（@tool 定义、add_messages/trim_messages），这一处把手写的 HTTP 客户端也换掉：
`app/ai/llm.py` 从"httpx 直连 /chat/completions"改成 **langchain-openai 的 `ChatOpenAI`**。

| 之前（手写 285 行） | 现在（薄适配 ~200 行） |
| --- | --- |
| httpx POST + 手写重试（429/5xx + 退避） | 框架的重试与超时（`max_retries` / `timeout`） |
| 手写 `tools` 负载与 `tool_calls` 解析（arguments 是 JSON 字符串） | `bind_tools(...)` + 框架解析好的 `AIMessage.tool_calls`（参数已是字典） |
| 手写 `response_format` 与 JSON 容错 | `.bind(response_format={"type": "json_object"})`，仍保留 `extract_json` 容错 |
| 手写 usage 解析 | 读 `AIMessage.usage_metadata` 映射成 TokenUsage |
| 没有流式 | 新增 `stream_text()`（给前端逐字输出留的接口，SSE 与前端渲染未接） |

**这一层为什么还留着**：调用方（诊断链路、Agent 图、MCP）只依赖两个方法
（`complete_json` / `complete_with_tools`）与 `last_usage`，所以"换模型/换厂商/换回裸 HTTP"
都只改这一个文件；降级语义（一切失败 → `LLMError` → 业务层退化成只返回相似案例）
与用量口径（token 进返回体）也留在这里。换成 `ChatOpenAI` 后，`@tool` 定义的工具可以直接
`bind_tools` 喂给模型——工具定义与模型调用两层用的是同一套框架对象了。

配套改动：`tools.py` 增加 `as_langchain_tool()`，把内部 ToolSpec 转成 LangChain 工具
（参数 JSON Schema → Pydantic 模型 → `StructuredTool`），**执行仍走 `run_tool`**；
图与手写循环改为把 LangChain 工具对象交给模型；测试里读取消息与工具的地方改成按对象属性读
（LangChain 消息用 `human/ai`，与 OpenAI 协议的 `user/assistant` 是对应关系）。

### 验证

- 三条路径真实调用：`complete_json` 534 ms（JSON 解析 + 用量 86 token）、
  `complete_with_tools` 786 ms（解析出工具名与参数，用量 330 token）、`stream_text` 654 ms（22 个片段）；
- 端到端：`/ai/ask` 走图编排 + `bind_tools`，2.7 秒返回；`/ai/diagnosis` 仍为混合检索 + 重排，
  返回体带 740 token 用量；
- 全量 198 项测试通过（假客户端注入，仍不消耗额度）。

## 十五、删掉与框架重复的实现

前面几轮把工具定义、消息、编排、模型调用都换成了框架写法，这一轮把因此变成"重复实现"的代码删干净。

### 删掉的东西

| 删除 | 为什么可以删 |
| --- | --- |
| `agent._answer_with_loop()` 手写循环（约 90 行）与 `answer()` 里的模式分发/回退分支 | 与状态图做的是同一件事；留着只会让"现在跑的是哪条路径"变成需要解释的问题，而且两套要同时维护与测试 |
| 配置项 `AI_ORCHESTRATOR`、响应字段 `orchestrator`、前端"编排 xx"标签 | 只有一套实现，字段恒为常量；前端少一个无用标签 |
| `llm.extract_json()`（正则剥代码块 + 花括号扫描） | 换成框架的 `JsonOutputParser`；JSON 模式（`response_format=json_object`）下模型只返回 JSON，不需要"从散文里抠 JSON"那层容错 |
| `embedding.OpenAICompatibleEmbedder`（约 85 行手写 HTTP/分批/重试） | 换成框架的 `OpenAIEmbeddings`；实测向量逐位一致（相似度 0.3609 vs 0.3608） |
| `embedding.LocalBGEEmbedder` 与配置项 `EMBEDDING_DEVICE` | 依赖（sentence-transformers）没装、路径从没跑过；本地模型改为"需要时接 langchain-huggingface 的 `HuggingFaceEmbeddings`，实现同一个 `Embedder` 协议"，不预埋死代码 |
| `ToolSpec.schema`（OpenAI 字典形式）、`TokenUsage.merge` | 工具都走 LangChain 对象、用量只累加不合并，已无引用 |

### 保留的判断依据

删的是"框架已经提供、自己写没有业务价值"的部分；**业务语义一条没删**：
工具的权限裁剪与审计（`run_tool`）、步数预算与收尾分支、抗幻觉两条约束、
认知到"降级"需要的失败语义。`agent.answer()` 仍然是入口，只是现在只做两件事：
没有模型时按降级返回；图执行抛异常时返回降级说明（而不是给用户 500）。

### 验证

- 全量测试 **195 项通过**（删掉 3 项与手写循环相关的用例）；
- 向量自检：框架客户端与原实现输出逐位一致，相似度 0.3609 / 0.1954；
- 端到端：诊断 `found=True`、`通道=hybrid`（关键词 2 / 向量 10）、重排丢弃 5、724 token；

## 十六、知识库：把语料维护做成页面功能（2026-10-11 补记）

### 起因

此前语料只有两个来源：故障记录表与内置仿真案例。演示时被问到「规范、手册能不能也喂进去」——
语料不能只有代码里的那 40 条，页面得能自己维护。

### 做了什么

| 序号 | 内容 | 位置 |
| --- | --- | --- |
| 1 | 数据模型：`knowledge_documents` 与 `knowledge_chunks` | `app/models/knowledge.py` |
| 2 | 解析与分块：txt/md/docx/pdf → 500 字分块、50 字重叠 | `app/services/knowledge.py` |
| 3 | 接口：列表 / 详情 / 概览 / 粘贴 / 上传 / 删除，权限点 `knowledge.view/upload/delete` | `app/api/v1/knowledge.py` |
| 4 | 语料接入：分块转 `CaseDocument`（`source=knowledge`），并入 `build_corpus` | `app/ai/corpus.py` |
| 5 | 增量向量化：按 `doc_id` 比对正文指纹，只对新增/改动的分块调接口 | `app/ai/index_store.py` |
| 6 | 页面：统计卡片 + 列表 + 详情分块预览 + 上传/粘贴弹窗 + 删除确认 | `frontend/src/views/knowledge/KnowledgeList.vue` |

### 四个设计取舍

**检索的最小单位是分块，不是整篇文档。** 一篇规范动辄上千字，整篇进索引有两个问题：BM25 的长度归一化
会被长文档带偏，向量也会被平均掉。切成 500 字、块间 50 字重叠，命中后用 payload 里的 `document_id`
回指原文。分块参数是常量，不好用就改两个数。

**解析失败不是异常，是一条可见的记录。** 扫描件 PDF、空白文档提取不到文字时，服务不返回 500，
而是把文档以 `failed` 落库、原因写进 `error`，列表页把失败条数做成统计卡片。理由很直白：
知识库里混进空文档比报错更糟——用户以为传上去了，检索却永远不命中，问题会拖到演示现场才暴露。

**删除用软删除。** `is_deleted` 置位即退出语料，记录仍在库里，审计中间件记录了是谁在什么时候删的。
硬删除省不了多少空间，但把「误删了怎么办」变成一个无法回答的问题。

**向量重算改成增量。** 原来每加一条语料都要把全量重新向量化一遍：41 条时无感，几百条时就是每次
上传都要等一轮接口。现在按 `doc_id` 比对正文的 sha1，没变的复用内存里的向量，只有新增/改动的分块
才调接口，日志会打一行「语料索引重建：共 N 条，其中新向量化 X 条（复用 Y 条）」。

### 过程里修掉的三处问题

1. **迁移缺 `server_default`。** 新表 `created_at` 直接写了 `nullable=False` 没给默认值，
   模型侧是 `server_default=func.now()`（INSERT 不带这两列），于是报
   `Field 'created_at' doesn't have a default value`。对照初始迁移改用 `server_default=sa.text("now()")`。
2. **回退脚本先删索引会失败。** `knowledge_chunks` 的复合索引被外键复用，MySQL 报
   `Cannot drop index ... needed in a foreign key constraint`；回退改成直接删表，索引随表一起走
   （初始迁移里已踩过一次，注释里写着，这次照做）。
3. **`content_type` 长度不够。** docx 的 MIME 是
   `application/vnd.openxmlformats-officedocument.wordprocessingml.document`，71 字符，原有 64 不够，
   新表放宽到 128。

### 验证

- 新增 16 项用例（`tests/test_knowledge.py`）：分块重叠与标点切分、docx 段落+表格解析、
  不支持格式 422 且不落盘、空文档落 `failed`、软删除后退出语料、只读用户可看不可传不可删、

## 十七、短期会话记忆：把追问从"前端带历史"挪到服务端（2026-10-11 补记）

### 起因

原来的多轮是**无状态**的：前端把最近几轮问答正文随请求带上，服务端每轮重拼一遍。
它能用，但有两个说不通的地方：一是"记忆"其实存在浏览器里，换个客户端就从零开始；
二是服务端无法自己控制历史长度，只能被动接受客户端传来的内容。

第一版实现是自己写了个 `(问题, 答案)` 列表的进程内存储。当天又改成了
**LangGraph 的 checkpointer**——理由见下面第四节。

### 做了什么

| 序号 | 内容 | 位置 |
| --- | --- | --- |
| 1 | 会话内容：图编译时挂 `InMemorySaver`，按 `thread_id` 存每轮状态 | `app/ai/graph_agent.py` |
| 2 | 会话目录：ID 发放与归属、TTL 30 分钟、最多 200 个会话 | `app/ai/memory.py` |
| 3 | 每轮重写消息窗口 + 裁剪，检查点不无限增长 | `graph_agent._prepare` |
| 4 | 接口：`/ai/ask` 接受 `conversation_id` 并回传；新增 `DELETE /ai/conversations/{id}` | `app/api/v1/ai.py` |
| 5 | 返回体新增 `conversation_id` 与 `memory_source`（server / client / none） | `app/schemas/ai.py` |
| 6 | 前端：会话 ID 存 sessionStorage，刷新页面还能续；"清空会话"顺手删掉服务端记忆 | `AssistantView.vue` |
| 7 | 配置：`AI_MEMORY_TTL_MINUTES`、`AI_MEMORY_MAX_CONVERSATIONS` | `app/core/config.py` |

### 三个决定

**服务端记忆优先，请求体历史兜底。** 两个来源都保留：有会话走服务端，服务端没有这个会话
（比如刚重启）就用前端带上来的历史，两条都不通就是单问单答。这样既拿到了"记在服务端"的好处，
又不会因为一次重启就把用户正在进行的对话打断。返回体里的 `memory_source` 把这件事说清楚，
页面上直接显示"带入 2 轮服务端记忆"或"带入 1 轮历史"。

**会话 ID 由服务端发放。** 客户端传回来一个服务端不认识的 ID，一律当新会话，另发一个 UUID。
好处是语义简单：ID 是服务端的资源，不是客户端可以自选的键；坏处是重启后 ID 会换新，
但那正好由"请求体历史兜底"补上连续性。

**进程内存储是明说的边界。** 单进程部署有效，多 worker 或多实例要换 Redis，
`ConversationMemory` 的接口不用动。TTL 与容量上限保证内存不会无限增长，
超容量时淘汰最久未活跃的会话。

### 为什么最后换成 checkpointer

第一版把问答正文存成自己的列表，等于在图之外又维护了一份"对话是什么样"的定义。
换成 checkpointer 之后，**图状态本身就是会话状态**：消息、工具调用、工具返回都由框架按
`thread_id` 存取，不用自己拼消息、也不用回答"到底哪些字段算记忆"。
两处配套的改动是必须的：

1. `_plan` 拿到最终结论时要把 `AIMessage` 放进消息列表——旧实现每轮重拼消息，
   压根没把回答写进去，挂上检查点后第一次跑就暴露了（第二轮模型看不到第一轮的回答，
   `history_turns` 也少算一轮）；
2. `_prepare` 每轮用 `RemoveMessage(REMOVE_ALL_MESSAGES)` 重写消息列表，
   再按「系统提示词 → 检查点里的历史 → 本轮问题」重建并 `trim_messages` 裁剪。
   重写是为了让技能正文每轮都跟着当前话题刷新（系统提示词里的技能内容会变），
   裁剪是为了让检查点不无限增长——否则一个长会话会把几个月前的消息一直带着。

**口径也跟着变了，说清楚：** 检查点里连着上一轮的工具返回，模型确实看得到上一轮查到的数字。
不再靠"不回灌工具细节"来防陈旧数据，而是靠提示词那条硬要求——涉及库存、工单、设备状态这类会变的数据，
必须重新调用工具取当前值。这是 checkpointer 带来的自然结果，也是取舍：换来的是模型能顺着上一轮的结果往下问。

**过期、淘汰、主动忘记三条路径都要删线程。** `InMemorySaver` 没有 TTL 与容量概念，
会话目录（`app/ai/memory.py`）负责这三件事，删目录的时候顺手 `delete_thread`，
否则检查点会留下孤儿线程。反过来，直接调 `agent.answer()` 不带 `thread_id` 时
开一个临时线程、跑完就删，单问单答不会在进程里攒垃圾。

### 安全上的两处细节

1. **会话绑定用户**：读别人的会话 ID 返回空历史，写回去只会新建一个自己的会话，不覆盖对方记录，
   也不区分"不存在"与"不是你的"——否则会话 ID 会变成探测手段；
2. **记忆不等于权限**：历史只是上下文，模型每次取数仍然走 `tools.run_tool` 的权限校验，
   伪造历史并不能越权读到数据。

### 验证

- 新增 15 项用例（`tests/test_ai_memory.py`）：会话目录侧有 ID 发放、归属、过期、
  最久未活跃淘汰、忘记会话幂等；检查点侧验证了"追问时模型确实看到上一轮"
  "工具调用与工具返回留在上下文里"（角色序列 system/user/assistant/tool/assistant/user）
  "长对话下最早的消息被裁掉""模型这一轮失败也要留下问题""跨用户拿别人的会话 ID 读不到内容"；
- 全量后端测试 **226 项通过**；前端 `typecheck` / `vitest` / `build` 全绿；
- 真实模型实测（开发库）：首问返回会话 ID（`memory_source=none`）→ 只带 ID 追问，
  `memory_source=server`、带入 1 轮（712 字）并正确回答耗材问题 → 第三轮带入 2 轮 →
  `DELETE` 后同一 ID 再问，服务端换发新 ID、带入 0 轮；删除动作在审计里可见。
  把检查点里那个会话的消息打出来看，是一条完整的图状态：
  `system → human → ai(工具调用) → tool(查询结果) → ai(结论)`。

## 十八、前端从 TypeScript 换成 JavaScript（2026-10-12 补记）

### 起因

前端当初是带着 `lang="ts"` 写的，`build` 里还挂着 `vue-tsc` 做类型检查。但 TS 不是我的既有技能，
写简历时只能算是"贴上去的关键词"——这类东西一旦被追问就露馅，于是决定把前端改回纯 JavaScript，
让代码、简历、面试口径三者对得上。

### 怎么改的

手改 40 个文件风险太大，改用项目自带的 TypeScript 编译器做语法层转译（`ts.transpileModule`），
它负责去类型注解、去接口、去泛型、擦掉类型导入，输出与原来逐行对应；类型化的 props 再手工补运行期声明。

| 改动 | 数量 | 说明 |
| --- | --- | --- |
| `.ts` → `.js` | 24 个 | api / store / composables / router / utils / main，`types.ts` 只放类型声明，直接删掉 |
| 去掉 `lang="ts"` | 16 个 `.vue` | 脚本块内容整体转译 |
| 补运行期 `defineProps` | 4 个组件 | `DataTable`、`EChart`、`MarkdownText`、`AttachmentPanel`——类型写法的 props 在 JS 里不存在，必须补 |
| 配置清理 | — | 删 `tsconfig.json`、`env.d.ts`，`vite.config` / `vitest.config` 改成 `.js`，`build` 去掉 `vue-tsc`，devDependencies 去掉 typescript / vue-tsc / @types/* |

### 踩到的坑（值得记）

**转译器会把"只在模板里用到"的 import 当成类型删掉。** 第一遍转完，构建居然成功了，
但产物小了 670 KB——`echarts` 与 `markdown-it` 整个没进包。原因是 TypeScript 的默认行为：
一个 import 如果在本文件的 JS 输出里没有被引用，就被判定为类型导入而擦除；
而 `<script setup>` 里 `import DataTable from '@/components/DataTable.vue'` 只在模板中用，
在脚本里"没被用到"，于是连组件一起消失了（页面不报错，只是整块内容不渲染）。
解法是转译时打开 `verbatimModuleSyntax`，逐字保留 import 语句。

**长度也对得上才算安全。** 改完对比了新旧产物体积：旧 1,880,166 字节、新 1,880,360 字节
（差值是 props 与模板的少量改动），再用脚本逐个文件核对 import，确认只少了该少的类型导入。

### 验证

- 新增前端冒烟用例（`components.spec.js`，6 项）：`MarkdownText` 渲染与 HTML 转义、
  `DataTable` 的 props 声明齐全、按 props 渲染表头与单元格、`stripe` 默认开启，
  以及**整应用挂载**——导入 `main.js`、等路由就绪，断言未登录时渲染出登录页
  （这一步把路由、store、Element Plus 与登录页一起验了）；
- 前端 `vitest` **12 项通过**、`build` 通过，产物体积与改造前一致；
- 后端未受影响（未改动），文档里的 `npm run typecheck` 与 `.ts` 文件名已同步。

## 十九、遗留事项

- 真实故障记录目前只有 1 条可用，语料 40 条全部来自仿真，`AI_INCLUDE_SYNTHETIC=false` 可切换；
- 评测集与行业词典同源，指标偏乐观；真实数据到位后要改成留出法重测（把最近 N 条历史记录留出当测试集）；
- 域外问题里同词异义的误召回需要向量检索或重排才能解决；
- 知识库只支持整篇删除，暂不支持编辑正文与重建索引的显式按钮（改完内容放新文档即可，指纹会识别为新增）；
- 数据合规：当前为演示数据，接入甲方真实数据前需确认是否允许出域，或改为内网部署模型；
- MCP 的 HTTP 传输用系统访问令牌（不是标准 OAuth），客户端接入要手工配令牌；
  上内网前补 OAuth，或把令牌范围再做细；
- 会话记忆是进程内的检查点，多 worker 部署前要换 `langgraph-checkpoint-redis` + Redis 会话目录。
